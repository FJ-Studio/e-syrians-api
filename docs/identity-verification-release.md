# ID verification rollout

Account → ID verification sells one €3 credit through Stripe Checkout on the web. The buyer can use the credit or gift it once using the recipient's private code. Admin grants in Filament are not transferable. A credit covers one check, not an approval. The API has separate live and sandbox wallets, histories and provider credentials. Do not migrate sandbox balances or decisions.

## Stripe

1. Use the existing Stripe account and a separate API key for this integration, installed on the Laravel server only as `IDENTITY_STRIPE_SECRET_KEY`. The integration needs Checkout Session write/read, Price read, and Payment Intent read (to correlate disputes). Configure `IDENTITY_STRIPE_PRICE_ID=price_1T2FrzIbFg7sfVM3s2Dhl4DW` in the environment that matches the Price's Stripe account and mode. Use a separate €3 one-time Price for the other mode. Do not change the donation route or copy secrets into Next.js or Expo.
2. Register a Stripe **snapshot** webhook destination at `https://api.e-syrians.com/webhooks/stripe/identity-verification` for `checkout.session.completed`, `checkout.session.expired`, `charge.refunded`, and `charge.dispute.created`. Install that destination's signing secret as `IDENTITY_STRIPE_WEBHOOK_SECRET`. Keep delivery active if new sales are paused; pending payments and reversals still need processing.
3. Check the Stripe receipt, support details, taxes, refund terms, and payout settings before taking money. The integration verifies the configured Price is active, one-time, and exactly EUR 300 cents before opening card Checkout for one credit. Adaptive currency conversion is off. It does not collect payments in the mobile app.
4. In a local/test database, use Stripe test credentials and the Stripe CLI to forward test events. Run a test payment, cancel/return, replay completion, refund, and verify wallet/history in both languages. The return URL is built from the API's `FRONTEND_URL`; production must use the public website's HTTPS origin. Do not use a live Stripe key on a local/test API or copy the local test database to production.
5. Monitor failed webhook deliveries and orders with `status = needs_refund`. If the buyer scheduled deletion or the account was deleted before a payment was confirmed, the API records the Payment Intent without granting a credit. Review these in Stripe and refund where applicable; the webhook does not issue refunds automatically. Refunds and disputes revoke unconsumed or active credits even after gifting. Used results remain as historical records, not as public badges. Resolving a dispute does not automatically reissue credit.

## Didit and release gates

- Use a separate Didit **Live** individual workflow and API key, configured as `DIDIT_LIVE_WORKFLOW_ID` and `DIDIT_LIVE_API_KEY`. Confirm the real workflow accepts the intended Syrian documents. Configure manual review, decide retention and ensure the key can retrieve decisions and request privacy erasure. Do not enable template retention unless approved and disclosed. Test account deletion and review access before collecting real documents.
- Publish the ID verification privacy notice and purchase/refund terms in both languages. Keep the decision separate from community verification. The API persists session references and status, not the full decision, document photos or biometrics. In-progress checks refresh via the authenticated Didit decision API; provider callbacks are not trusted as decisions. A public badge or policy based on identity claims needs separate rules for binding a document to the profile, expiry, and revocation.
- Deploy the wallet migration before enabling anything. Keep `IDENTITY_VERIFICATION_ENABLED=false` and `IDENTITY_STRIPE_CHECKOUT_ENABLED=false` by default. Enable the live API and `NEXT_PUBLIC_IDENTITY_VERIFICATION_ENABLED` only when the provider, disclosure and operational checks are done; enable Checkout separately after the Stripe test. Production refuses test Stripe credentials. After an env change, reload Laravel config and long-running workers as applicable.
- Keep `EXPO_PUBLIC_IDENTITY_VERIFICATION_ENABLED=false` in public store builds until mobile billing/store review is resolved. The mobile implementation can use the shared wallet and verification flow, but does not embed Stripe Checkout, a purchase link, or native purchase products.

# ID verification rollout

Account → ID verification sells one €3 credit through Stripe Checkout on the web. The buyer can use the credit or gift it once using the recipient's private code. Admin grants in Filament are not transferable. A credit covers one check, not an approval. The API has separate live and sandbox wallets, histories and provider credentials. Do not migrate sandbox balances or decisions.

Community verification remains the participation gate for publishing polls, voting or reacting, feature-request participation, and managing saved audiences. The API exposes it as `community_verified_at` and retains `verified_at` as a compatibility alias. Neither `id_verification_approved` nor the combined `verification_badge` grants any permissions.

## Stripe

1. Use the existing Stripe account and a separate API key for this integration, installed on the Laravel server only as `IDENTITY_STRIPE_SECRET_KEY`. The integration needs Checkout Session write/read, Price read, and Payment Intent read (to correlate disputes). Configure `IDENTITY_STRIPE_PRICE_ID=price_1T2FrzIbFg7sfVM3s2Dhl4DW` in the environment that matches the Price's Stripe account and mode. Use a separate €3 one-time Price for the other mode. Do not change the donation route or copy secrets into Next.js or Expo.
2. Register a Stripe **snapshot** webhook destination at `https://api.e-syrians.com/webhooks/stripe/identity-verification` for `checkout.session.completed`, `checkout.session.expired`, `charge.refunded`, and `charge.dispute.created`. Install that destination's signing secret as `IDENTITY_STRIPE_WEBHOOK_SECRET`. Keep delivery active if new sales are paused; pending payments and reversals still need processing.
3. Check the Stripe receipt, support details, taxes, refund terms, and payout settings before taking money. The integration verifies the configured Price is active, one-time, and exactly EUR 300 cents before opening card Checkout for one credit. Adaptive currency conversion is off. It does not collect payments in the mobile app.
4. In a local/test database, use Stripe test credentials and the Stripe CLI to forward test events. Run a test payment, cancel/return, replay completion, refund, and verify wallet/history in both languages. The return URL is built from the API's `FRONTEND_URL`; production must use the public website's HTTPS origin. Do not use a live Stripe key on a local/test API or copy the local test database to production.
5. Monitor failed webhook deliveries and orders with `status = needs_refund`. If the buyer scheduled deletion or the account was deleted before a payment was confirmed, the API records the Payment Intent without granting a credit. Review these in Stripe and refund where applicable; the webhook does not issue refunds automatically. Refunds and disputes revoke unconsumed or active credits even after gifting. Used results remain as historical records, not as public badges. Resolving a dispute does not automatically reissue credit.

## Didit and release gates

- Use a separate Didit **Live** individual workflow and API key, configured as `DIDIT_LIVE_WORKFLOW_ID` and `DIDIT_LIVE_API_KEY`. Confirm the real workflow accepts the intended Syrian documents. Configure manual review, decide retention and ensure the key can retrieve decisions and request privacy erasure. Do not enable template retention unless approved and disclosed. Test account deletion and review access before collecting real documents.
- Publish the ID verification privacy notice and purchase/refund terms in both languages. Keep the decision separate from community verification. The API persists session references and status, not the full decision, document photos or biometrics. In-progress checks refresh via the authenticated Didit decision API; provider callbacks are not trusted as decisions. A public badge or policy based on identity claims needs separate rules for binding a document to the profile, expiry, and revocation.
- Deploy the wallet migration before enabling anything. Keep `IDENTITY_VERIFICATION_ENABLED=false` and `IDENTITY_STRIPE_CHECKOUT_ENABLED=false` by default. Enable the live API and `NEXT_PUBLIC_IDENTITY_VERIFICATION_ENABLED` only when the provider, disclosure and operational checks are done; enable Checkout separately after the Stripe test. Production refuses test Stripe credentials. After an env change, reload Laravel config and long-running workers as applicable.

## Native store credits

### StoreKit Sandbox and App Review

TestFlight and App Review use StoreKit Sandbox, even with a release-signed app. The iOS client reads StoreKit's app transaction environment and sends `X-Identity-Store-Environment: sandbox` only to the authenticated identity-verification API. This header selects a wallet; it is never proof of a purchase.

Enable `IDENTITY_STORE_IOS_SANDBOX_ENABLED` only for review/testing, and add the dedicated review accounts' UUIDs to `IDENTITY_SANDBOX_TEST_USERS`. Configure Didit Sandbox separately from Didit Live. Unlisted accounts are denied. Apple transaction IDs are verified against Apple's sandbox API with the expected bundle, SKU, owner token, quantity and environment; sandbox credits and history remain in the existing sandbox tables. A test approval never becomes a public ID badge or a live credit. Test-mode Stripe checkout and Android fulfillment are unavailable through this context. The ordinary production wallet continues to reject sandbox receipts. Disable review access when no longer needed.

The same iOS binary detects Production when installed from the App Store and Sandbox when installed from TestFlight. Keep all Apple private keys on Laravel, never in Expo or the app. Review access and iOS sales flags are separate. Configure and test both before creating a submission; the first in-app purchase must be included with its app-version submission.

For server-side installation, set `IDENTITY_STORE_APPLE_ISSUER_ID`, `IDENTITY_STORE_APPLE_KEY_ID`, and either `IDENTITY_STORE_APPLE_PRIVATE_KEY` (the PEM, with literal or escaped newlines) or `IDENTITY_STORE_APPLE_KEY_PATH` (a readable, private server file). An explicitly invalid inline key disables sales rather than falling back silently. Never place PEM material in shell-command history or Git. Rebuild Laravel's config cache after installation and test a read-only App Store Server API request in both environments before enabling iOS sales.

### Apple signed-data verification and deployment

The private `.p8` key authenticates Laravel's requests **to** Apple. It does not authenticate Apple's signed transaction payload **to** Laravel. `AppleSignedTransactionVerifier` runs the pinned official `@apple/app-store-server-library` using Node **22+**, with public roots from `resources/certificates/apple` (source URLs and fingerprints documented there). The helper enforces ES256, trusted certificate chains, App Store certificate-purpose OIDs, current validity, online OCSP revocation checks, bundle and environment before returning a minimal verified payload. Laravel then checks transaction ID, product, owner account token, quantity, consumable type and refund status before wallet mutation. Duplicate deliveries remain idempotent. Xcode/LocalTesting verification bypasses are not supported.

Deploy `npm ci --omit=dev --ignore-scripts --no-audit --no-fund` as part of each API release (before activating it), or use the project's ordinary full `npm ci` when also building its assets. The Apple package is a production dependency. `IDENTITY_STORE_APPLE_NODE_BINARY` can specify an absolute Node 22+ binary if PHP-FPM's PATH differs; `IDENTITY_STORE_APPLE_APP_ID=6776366211` and the bundled trusted roots default to E-Syrians. An optional `IDENTITY_STORE_APPLE_ROOT_CERTIFICATES` override is a comma-separated list of trusted absolute PEM file paths, never a URL. These settings and the certificates are server-side only, not Expo/Next.js variables. No additional private Apple key is needed.

Checkout readiness checks run the actual verifier runtime and parse the public roots, rather than merely checking file existence. Missing dependencies/roots/runtime hide Apple sales and return `identity_store_unavailable`. A rejected signature/chain returns `identity_store_invalid_purchase` without credit; a timeout or certificate-status outage fails closed and leaves the transaction available for retry. Signed transactions and subprocess diagnostics are never logged, passed in process arguments, or returned to clients. The subprocess environment excludes Laravel credentials and Node preload hooks. Keep outbound Apple certificate-status access available; never disable revocation checking to make checkout succeed.

Run `npm run test:apple` and the PHP suite before release. The feature tests exercise the complete purchase → balance/history → duplicate delivery → gift → Didit status/refund flow against an in-memory database, real ES256 signatures, synthetic trust chains, and actual signed OCSP responses served on disposable loopback ports. Store and Didit API responses are test doubles: these are not a substitute for a real Apple Sandbox purchase on a supported device. Complete that device test before submission, with an allowlisted sandbox account and no real documents or payments.

1. Create one **consumable** in App Store Connect and one one-time Play product with a single **Buy** option (`buy-one`), not Rent or Pre-order. Both use `identity_verification_credit`: configure `IDENTITY_STORE_IOS_PRODUCT_ID` and `IDENTITY_STORE_ANDROID_PRODUCT_ID` to match. Prices and paid territories belong in the stores, not in Laravel. The app displays the localized price for the offer the store actually opens. The Irish price is €2.99 on the Apple draft and the intended Irish Play price is €3.00. Disable multi-quantity on Play. Leave purchase options inactive until ready for controlled testing. Attach the Apple review screenshot and the first IAP to the first app version submitted with it, when authorized. Don't add external Stripe checkout to mobile.
2. Install only server-side credentials. Apple requires the **In-App Purchase** private key (`IDENTITY_STORE_APPLE_KEY_PATH`), its key ID (`IDENTITY_STORE_APPLE_KEY_ID`), and the issuer ID (`IDENTITY_STORE_APPLE_ISSUER_ID`). For Play, assign a dedicated service account financial and order permissions for `com.esyrians.app` only. In the API's `.env`, set `IDENTITY_STORE_GOOGLE_CREDENTIALS_JSON` to the compact JSON object inside single quotes so the JSON's escaped newlines stay intact. Protect `.env` and the generated Laravel config cache; both can contain the credential. `IDENTITY_STORE_GOOGLE_CREDENTIALS_PATH` still works when the inline setting is empty, not when the inline JSON is malformed. Don't use the push notification account, publish keys to Expo, or share private keys in chat.
3. Apply the `identity_store_purchases` migration before using native purchases. Keep `IDENTITY_STORE_IOS_ENABLED` and `IDENTITY_STORE_ANDROID_ENABLED` off on production until each platform is verified. They pause new sales, not fulfillment of purchases already made. Laravel's scheduler must run `IdentityStoreCheckout::reconcile()` every minute for Google consumption retries and refund checks. Monitor the scheduler and store orders; support must review payments that can't be fulfilled after account deletion.
4. Test against an isolated local/staging API and database. Enable `IDENTITY_SANDBOX_ENABLED`, add synthetic users to `IDENTITY_SANDBOX_TEST_USERS`, configure Didit Sandbox, install the store API credentials and enable the store under test only there. Point the app at this API with `EXPO_PUBLIC_IDENTITY_VERIFICATION_ENABLED=false` and `EXPO_PUBLIC_IDENTITY_SANDBOX_ENABLED=true`. Use an [Apple Sandbox tester](https://developer.apple.com/help/app-store-connect/test-in-app-purchases/overview-of-testing-in-sandbox/) or [Play license tester](https://developer.android.com/google/play/billing/test), and proceed only when the store shows a test payment. Test receipts post to `/users/identity-sandbox/store-purchases`; production receipts post to `/users/identity-verification/store-purchases`. Both return the updated wallet and first page of history after registration. Sandbox payments, credits and decisions cannot enter the live wallet. Test a successful purchase, cancellation, pending payment, credit/history refresh, retry after restart, a gift and a complete Didit sandbox check. Never upload real documents in Sandbox.
5. Update purchase/refund terms before launch to distinguish web Stripe purchases from store purchases and point users to the proper support path. Store approval isn't account ID approval, and an available credit is not a completed check. The wallet displays account ID verification separately from the latest attempt.
